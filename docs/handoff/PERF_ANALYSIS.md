## 결론 먼저

**지금 규모에서 최적화는 필요 없어요.** 한 턴(플레이어 계획 + 재생) 규칙 계산이 약 30~80µs예요.
60fps 한 프레임(16.7ms)의 0.5%도 안 돼요. 렌더러 쪽 코어 호출도 프레임당 0.2% 이하예요.
그래도 골든 스냅샷을 그대로 두면서 시뮬레이터가 20~40% 빨라지는 "공짜" 변경이 하나 있어요(아래 1번).
코드도 더 단순해져요. 하고 싶다면 그것만 권해요.

## 1. 측정 환경과 방법

- Node 22.23, Firecracker VM 4코어. **이웃 소음이 커서** 같은 코드도 회차마다 ±30% 흔들렸어요.
  그래서 ① 프로세스를 번갈아 여러 번 돌려 최솟값을 보고 ② valgrind(callgrind, `--jitless`)로 명령어 수도 셌어요.
- `npx tsx`는 esbuild `keepNames`로 함수마다 `__name()` 호출을 끼워서 6% 넘게 부풀려요.
  실제 빌드(Vite)와 비슷하게 하려고 esbuild로 묶어서(keepNames 끔) 쟀어요.
- 작업량: 인카운터 11개 × 시드 200 × 파티 4개(기본 + 지정 3개) = 8,800판.
  지정 파티: `fire_fox,glass_salamander,mist_cat` · `star_spirit,pearl_oyster,glass_salamander` · `magma_ibex,prism_chameleon,fire_fox`
- `autoBattle`은 유체(baby)·장비 없음이에요. 그래서 성격·장비 경로가 거의 안 돌아요.
  성체(adult)·각성체(awakened) 시나리오를 따로 쟀어요(`adult.tmpl.ts`).
- 장비 데이터(`src/data/equipment`)는 아직 비어 있어요. `equipMods` 비용은 지금 0에 가까워요.

요청하신 항목별 판정:

- **`runStages` 매번 정렬**: 실측 가장 큰 공짜 낭비예요. 3~12개짜리 배열이지만 비교 함수 호출이 인라인되지 않아요.
  `resolveStat`(STAT_LAYERS)과 `runSteps`도 같은 꼴이에요.
- **`stat()` 재계산**: `stat` 한 번이 `resolveStat` 전체(정의 조회, 층 정렬, `parts` 배열)를 다시 해요.
  전투 중 `RunSpirit`은 바뀌지 않아서 기본값은 캐시해도 같아요(전투 코드에 `run.*` 쓰기가 없어요).
- **`passivesOf`/`allPassives`**: 호출 수가 가장 많아요(턴당 166). 대부분 `cardCostOf`에서 와요(카드 비용 1번 = `passivesOf` 4번).
  지금은 붙은 게 적어 배열이 작지만, 성격·해방·장비가 붙으면 비용이 커져요(각성체에서 효과가 가장 커요).
- **`cardDef()` Map 조회**: 10ns × 250 = 판당 2.5µs. 손댈 가치가 없어요.
- **`equipMods` 스캔**: 장비 데이터가 비어 있어 지금은 0이에요. 장비가 들어오면 `stat`마다 장비×층×보정을 훑어요.
  기본값 캐시가 있으면 조건부 층(`equipConditional`)만 남아요.
- **이벤트·로그 문자열**: `log`를 비우는 실험에서 4~10%였어요(소음 큼). 로그는 골든 이벤트 스냅샷에 들어가요. 그대로 두는 게 맞아요.
- **`Object.keys(status)`**(`tickStatuses`·`clearStatuses`): 자기 시간 1% 남짓. 무시해도 돼요.
  `runStatusHook`은 `STATUS_IDS` 23개를 훑지만 표 순서가 규칙이라 바꾸면 위험해요.
- **rng·셔플**: mulberry32 한 번이 수 ns예요. 셔플은 판당 몇 번뿐이에요. `weighted`는 맵 생성에서만 써요.
- **효과문 `describeCard`**: 카드당 평균 1.3µs예요.

## 4. 렌더러 쪽

- **레거시 `placeholder/scenes/BattleScene.ts`**: `update()`가 없어요. `refresh()`는 입력·재생이 끝날 때만 돌아요(프레임마다가 아니에요).
  `drawHand()`는 카드마다 `stat`×3 + `canPlay`(안에서 `cardCost`) + `cardCost` + `describeCard`를 불러요.
  손패 5장 한 번에 코어 호출만 **21.6µs**예요. 7장이면 약 30µs예요.
  툴팁은 `stat`×3(~1.5µs), 적 HUD는 `intent()`(766ns)를 적마다 불러요.
- **새 `presentation/battle/`**: 아직 정본 고정 장면(fixtures)으로 그려요. `src/core`를 부르지 않아요.
  `pointermove`마다 `refresh()`가 돌지만 코어 비용은 0이에요.
- **60fps 판정**: 프레임마다 손패 전체를 다시 계산해도 ~30µs = 프레임 예산의 0.2%예요. **메모이제이션은 필요 없어요.**
  레거시가 `handLayer.removeAll(true)`로 텍스트 객체를 새로 만드는 비용이 훨씬 클 거예요(측정 안 함, 코어 범위 밖).
- **앞으로 볼 곳**: session 층이 생겨 `OutcomeVM`(끌기 미리보기)을 `pointermove`마다 규칙으로 계산한다면,
  전투를 복제해 시뮬레이션하는 방식은 복제 비용(`new Battle` 약 6µs, 상태 깊은 복사)이 생겨요.
  그때도 1ms 아래라 문제는 아니지만, 대상이 바뀔 때만 다시 계산하면 충분해요.

## 6. 권장 순서

1. **아무것도 안 해도 돼요.** 게임 플레이에서는 체감 차이가 없어요.
2. 손을 댄다면 **1번(정렬 한 번)만** 하세요. 골든 그대로, 코드가 짧아지고, sim·테스트가 눈에 띄게 빨라져요.
   단계 목록이 정렬돼 있는지 확인하는 테스트를 같이 넣어요.
3. 2·3번은 장비가 들어와 `stat`이 무거워질 때 다시 봐요. 4번은 그때 테스트를 고치면서 같이 봐요.
4. 렌더러 메모이제이션은 하지 않아요. session 층을 만들 때 "대상이 바뀔 때만 미리보기 계산" 원칙만 지켜요.
